# ADR 001: Behavior Plans drive browser previews

- Status: Accepted
- Date: 2026-08-31
- Owners: Schematic product and engineering
- Supersedes: compiler- or firmware-driven browser preview proposals

## Context

Schematic needs to help a person understand an intended hardware outcome before
physical hardware is connected. Source generated by an agent is useful as an
editable handoff artifact, but compiling or emulating arbitrary embedded code in
the browser would support only a narrow set of boards and libraries while making
the visual result easy to overstate.

The product also needs one behavioral truth shared by the human interface and
WebMCP. If an agent independently writes source and changes visual components,
the code panel and preview can silently disagree.

## Decision

A finite, versioned, validated Behavior Plan is the sole durable input to a
browser Behavior Preview. The preview runtime combines the prepared plan with
an ordered, bounded session invocation/input log and reduces both through exact,
checked-in component behavior profiles.

Source code is stored as an independently editable document. Schematic may link
a source revision to an exact Behavior Plan hash for provenance, but it never
parses, compiles, interprets, emulates, uploads, or executes that source to
produce the browser preview.

The shared `@schematic/behavior` boundary owns plan validation, canonical
serialization and hashing, exact profile registration, deterministic session
reduction, snapshots, limits, and structured diagnostics. React, Zustand,
Monaco, WebMCP, networking, compiler packages, and hardware runtimes remain
outside that package. UI actions and WebMCP tools call the same application
commands so they cannot develop competing semantics.

Catalog preview support is explicit by definition ID, profile ID, and profile
version. Unknown definitions or unsupported actions fail visibly; category,
port, name, or text inference never grants behavior support.

Every preview surface states:

> Scripted outcome · no code ran · wiring and hardware not verified.

Every code surface states that source is editable and intended for later
external use, and that Schematic has not compiled, uploaded, run, or physically
tested it.

## Consequences

- The browser can show deterministic, replayable outcomes for more components
  without claiming MCU, electrical, timing, or physical fidelity.
- Manual source edits cannot alter preview output. Plan edits cannot overwrite
  source. Hash links become stale when either exact revision changes.
- Compilation, upload, and physical verification belong to external IDE, SDK,
  CLI, or connected-hardware workflows and are not code-panel lifecycle states.
- Graph/electrical diagnostics remain separate from Behavior Plan diagnostics.
  A visually successful conceptual preview never clears wiring warnings.
- Legacy compiler and simulator scaffolds may remain as dormant historical code,
  but the default Site bundle and recommended WebMCP workflow must not import or
  invoke them.

## Rejected alternatives

### Compile source in the browser

Rejected as the default because toolchains, libraries, boards, binary size,
runtime cost, and browser constraints make broad support impractical. Compilation
also does not by itself create an understandable visual outcome.

### Parse generated source to infer preview behavior

Rejected because partial language interpreters create false confidence and
couple the preview to formatting, libraries, and dialects. Ordinary agent code
must remain unrestricted by a preview parser.

### Let the model invoke arbitrary JavaScript component functions

Rejected because it bypasses validation, determinism, capability discovery,
resource limits, and replay. Agents may invoke only typed actions/events exposed
by exact component profiles.

### Generate source and preview commands independently

Rejected because the two artifacts can contradict each other. A Behavior Plan
is the behavioral source of truth; generated source may record provenance to its
exact hash without becoming preview input.

## Verification

The release gate requires deterministic golden hashes, exact profile-resolution
tests, invalid-plan and resource-budget tests, UI/WebMCP parity, code-hash
conflict tests, persistent honesty copy, and proof that the initial Site bundle
does not import the dormant compiler/emulator packages.

The detailed contract, migration rules, tool schemas, UX copy, and implementation
checklist live in [TYPESCRIPT_WEB_SIMULATION_HANDOFF.md](TYPESCRIPT_WEB_SIMULATION_HANDOFF.md).
